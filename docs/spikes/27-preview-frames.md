# 프리뷰 프레임 생성 방식 — 결정과 실측 (#27)

> 스파이크 #25 6장이 세 길을 남기고 "#27이 고른다"로 넘겼다. 이 문서가 그 결정과 근거다.
> 원자료는 [`27-preview-frames/preview-results.json`](27-preview-frames/preview-results.json),
> 벤치는 [`frame_bench.py`](27-preview-frames/frame_bench.py)다.

---

## 1. 결정

**장면 대표 프레임 배치 캐시** — 스파이크 #25의 1번(장면 대표 프레임 캐시)에, 그 문서가
전제하지 않았던 조건 하나를 더한 것이다.

> **요청한 장면이 하나든 전부든 프로세스는 하나다.**

스파이크는 "장면당 한 장을 만들어 두고 편집이 닿은 장면만 다시 만든다"고 적었는데, 실측해
보니 **다시 만들 장면을 골라 봐야 아끼는 것이 거의 없다.** 뒤쪽 장면 하나를 만드는 데
2,049ms, 열한 장면 전부를 만드는 데 2,247ms다. 그래서 "닿은 장면만"이 아니라 **매번 전부**
만들고, 아끼는 것은 재생성 범위가 아니라 **프로세스 수**다.

- 구현: `video_renderer.preview()` — 요청 장면들의 대표 프레임 번호로 `select` 식을 만들어
  FFmpeg 하나에 넘긴다
- 캐시: `api._PREVIEW` — 프로젝트 + 장면 목록의 지문 하나 분량만 들고 있고, 지문이 바뀌면
  통째로 버린다
- 기각: **상주 프레임 서버**(수명·에러 복구가 앱에 붙고, 아래 숫자면 살 이유가 없다),
  **더 작은 FFmpeg 빌드**(기동 비용을 줄이지만 배포 라이선스를 다시 재야 하고, 지금 병목이
  아니다 — 5.2의 재검토와 함께 미룬다)

## 2. 실측

3회 중앙값. 입력은 스파이크 #25가 남긴 실제 파이프라인 산출물 —
`sample-run/run-20260812-082525` (11장면 / 27.949초 / 837프레임 / 1080x1920).
**제품 코드(`video_renderer.preview`)를 그대로 부른 값이다.**

| 측정 | 값 |
| --- | --- |
| 장면별 프로세스 — 11장면 합계 | **19,131ms** |
| 장면별 프로세스 — 장면 하나 | 1,819ms |
| **배치 한 프로세스 — 11장면 전부** | **2,247ms** |
| 배치 한 프로세스 — 장면당 환산 | 204ms |
| 부분 요청 — 첫 장면 하나 | 1,381ms |
| 부분 요청 — 마지막 장면 하나 | 2,049ms |
| `ffmpeg -version` (일 없음) | 1,266ms |
| 캐시 적중 (FFmpeg를 지나지 않음) | **3~5ms** |

**절대값은 실행마다 ±20% 흔들린다** — 바닥이 프로세스 기동이라 머신 부하를 그대로 탄다.
반복 실행에서 합계가 19.1~23.5초, 배치가 2.2~2.7초로 움직였다. 결론이 걸려 있는 것은 절대값이
아니라 **비율**이고, 그쪽은 흔들리지 않았다.

세 가지가 읽힌다.

1. **바닥은 여전히 프로세스 기동이다.** 아무 일도 하지 않는 `ffmpeg -version`이 1.3초이고,
   장면 하나를 뽑는 데 1.4~2.0초다 — 실제 필터링은 그 차이뿐이다. 스파이크 #25가
   잰 것과 같은 결론이고, 그래서 프로세스 수가 유일하게 줄일 수 있는 축이다.
2. **비용은 마지막 요청 장면의 위치가 정한다.** 첫 장면 1,381ms / 마지막 장면 2,049ms이고,
   전부 요청해도 2,247ms다 — 필터는 요청한 마지막 프레임까지 어차피 돈다(`-frames:v`가 거기서
   끊는다). **뒤쪽 장면 하나를 위해 전부를 만드는 추가 비용이 198ms**라서, 무엇을 다시 만들지
   고르는 코드는 값을 하지 못한다.
3. **8.5배다.** 11장면 기준 19.1초 → 2.2초. 장면이 늘수록 격차가 선형으로 벌어진다.

### 2.1 두 방식이 같은 그림을 낸다

배치로 뽑은 11장과 장면별로 뽑은 11장이 **파일 크기까지 전부 같았다**
(`frames_identical: true`). 명령이 `video_renderer._video_stage` 하나를 지나기 때문이고,
같은 이유로 프리뷰와 최종 렌더도 갈릴 수 없다.

## 3. 화면에서 무엇이 되는가

D2 확정 스펙 6장이 "결과가 정지 프레임이고 대기가 1~2초"만 전제했으므로 어느 방식을 골라도
화면은 같다. 실제로 사용자가 겪는 것은 두 가지뿐이다.

| 상황 | 대기 |
| --- | --- |
| 프로젝트를 열고 첫 장면을 본다 | 2.2초 (전부 만든다) |
| **다른 장면을 고른다** | **3~5ms** — 캐시 적중 |
| 값을 고친다 (자막 스타일·배경·cta 문구…) | 2.2초 (지문이 바뀌어 전부 다시 만든다) |

두 번째 줄이 이 결정이 산 것이다. 장면별 프로세스였다면 장면을 고를 때마다 1.8초를 냈다.

대기 표현이 두 가지인 이유도 여기서 나온다 — 장면 이동은 즉시라 이전 프레임을 지워도
빈 화면이 보이지 않고, 값 변경은 2초대라 지우면 비교할 대상이 사라진다.

## 4. 캐시를 어디에 두는가

**run 디렉터리 밖이다** (`tempfile.mkdtemp`, 백엔드 프로세스 수명).

TTS 캐시(`.cache/tts`)가 run 디렉터리 밖인 것과 이유가 다르다 — 그쪽은 run마다 새 디렉터리라
안에 두면 매번 전부 재합성하기 때문이고, 이쪽은 **프레임이 파생물이고 수명이 앱 세션**이기
때문이다. run 디렉터리에 남기면 사용자가 만들지 않은 파일이 산출물 옆에 쌓이고, PRD 6.2의
산출물 표에 없는 것이 생긴다.

**지문 하나 분량만 들고 있다.** 편집은 앞으로만 가므로 지난 지문의 프레임은 다시 요청되지
않는다. 전부 남기면 편집 한 번에 11장씩 쌓이고 버리는 기준을 따로 정해야 한다.

지문은 **프로젝트를 통째로 해싱한다.** 프리뷰에 영향을 주는 필드를 골라 적으면 렌더가 읽는
필드가 늘었을 때(#29의 트랙 볼륨, #34의 모션) 화면이 옛 그림에 머문다 — 틀린 그림을 캐시가
지켜 주는 쪽이 값을 하나 더 해싱하는 것보다 비싸다.

## 5. 뒤에 남기는 것

- **재검토 조건.** 장면이 30개를 넘거나(현재 11) 총 길이가 2~3분대가 되면 배치 한 번이
  6초를 넘길 수 있다. 그때 상주 프레임 서버(스파이크 #25 6장의 2번)를 다시 잰다 — 지금은
  기동 비용을 한 번만 내는 이점이 2초대 대비 값을 하지 못한다.
- **#30(앱에서 렌더)** — 진행률(`-progress pipe:1`)은 프리뷰와 다른 축이다. 이 결정이
  그쪽을 막지 않는다. 오래 걸리는 메서드를 스레드로 보내는 자리(`api.BACKGROUND_METHODS`)는
  #27이 열어 뒀고 `render`가 같은 목록에 들어간다.
- **#36(렌더 실패 처리)** — 프리뷰 실패는 `code: "render"`로 온다. 실행 명령과 stderr를 run
  디렉터리에 남기는 것은 그쪽 몫이고, 지금은 `run.log`에만 남는다.
