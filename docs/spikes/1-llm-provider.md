## 1. 결론

**MVP 기본 provider는 로컬에 설치된 `claude` CLI를 헤드리스(`-p`)로 호출하는 방식으로 한다.
기본 생성 모델은 `claude-opus-5`(별칭 `opus`)로 한다.**

근거 — 세 가지가 동시에 성립한다.

1. **품질이 유일한 변별축이었다.** 구조화 출력 실패율은 세 후보 모두 0%였고 정답 정확도도
   갈리지 않았다. 실제로 갈린 것은 문제의 다양성과 난이도 보정이며, 여기서 `opus`가
   명확히 앞섰다 (4.1).
2. **품질 대가로 치르는 것이 사실상 없다.** `opus`의 문제당 지연은 26.9초, `haiku`는 27.0초로
   **차이가 없다**. 비용은 문제당 $0.0229 대 $0.0118로 약 2배지만 절대액이 영상 1편당
   $0.09 대 $0.05 수준이라 의사결정을 좌우하지 않는다 (4.3, 4.4).
3. **API 키 관리가 필요 없다.** 이미 설치·인증된 CLI를 재사용하므로 키 발급·보관·로테이션이
   MVP 범위에서 빠진다.

`sonnet`은 비용이 중간임에도 **탈락**시킨다. 동일 프롬프트 3회 실행에서 "물의 화학식은?"이
3회 전부, "세종대왕이 창제한 문자는?"이 3회 전부 반복 출제됐다. 쇼츠를 연속 생산하는
도구에서 이 정도 반복은 치명적이다 (4.1).

### 이 결론이 규정하지 않는 것

- **오프라인 동작은 확보되지 않았다.** "로컬 claude"는 로컬에서 도는 LLM이 아니라 로컬 CLI를
  통한 Anthropic 원격 API 호출이다. 이슈 #1의 비교축 중 **오프라인 가능성은 미충족이며
  측정되지도 않았다.** 오프라인이 요구사항으로 승격되면 이 결정을 다시 열어야 한다.
- **vendor 다양성은 측정하지 않았다.** 후보 3개는 모두 Anthropic 모델이다. OpenAI·Gemini·Ollama와의
  비교는 수행하지 않았다. 따라서 이 결정은 "Anthropic 계열 중 무엇을 쓸까"에 대한 답이지
  "어느 vendor를 쓸까"에 대한 답이 아니다. 인터페이스(5장)를 vendor 중립으로 두는 이유다.

## 2. 실험 방법

`claude` CLI 2.1.220을 헤드리스로 호출한다. 후보는 `--model` 별칭으로 지정했고 실제
해석 결과는 다음과 같다.

| 별칭 | 실제 모델 ID |
| --- | --- |
| `opus` | `claude-opus-5` |
| `sonnet` | `claude-sonnet-5` |
| `haiku` | `claude-haiku-4-5-20251001` |

후보별로 동일 프롬프트로 상식 퀴즈 4문제 생성을 **3회** 반복하고, 1회차 문제 4개에 대해
**블라인드 재답변 검증을 문제당 2회** 수행했다. 후보당 11회, 총 33회 호출.

### 2.1 컨텍스트 격리 — 이걸 빼면 측정이 무의미해진다

프로젝트 디렉터리에서 그냥 `claude -p`를 부르면 `CLAUDE.md`, 스킬 목록, 툴 정의, MCP 설정이
전부 프롬프트에 실린다. 실측으로 **"1+1은?" 한 줄에 캐시 생성 6,185 + 캐시 읽기 17,442 토큰,
$0.071**이 들었다. 아래 플래그로 이를 벗겨내면 같은 성격의 호출이 **$0.004**로 떨어진다.

```
--safe-mode --tools "" --disable-slash-commands
--strict-mcp-config --setting-sources "" --no-session-persistence
--system-prompt <프롬프트>   # 기본 시스템 프롬프트를 대체
```

**이 격리는 측정용 편의가 아니라 운영 요구사항이다.** #9·#13에서 실제로 호출할 때도
동일하게 적용해야 한다. 빠뜨리면 비용이 한 자릿수 배로 튄다.

### 2.2 구조화 출력

`--json-schema`에 `quiz.json`의 콘텐츠 스키마(퀴즈 스펙 3.1에서 `verify` 필드 제외)를 넘긴다.
CLI가 검증까지 마친 값을 응답 JSON의 `structured_output` 필드에 넣어준다. 파싱·재시도 로직을
파이프라인에서 직접 구현할 필요가 없다.

### 2.3 블라인드 검증

생성된 정답을 **보여주지 않고** 질문만 다시 물어 독립 답변을 받은 뒤 대조한다.
"이 정답이 맞습니까?"로 물으면 같은 모델이 자기 출력에 동조해 검증 효과가 없다.
표기 범위 차이("세종대왕(조선 제4대 왕 세종)" vs "세종대왕")를 오답으로 세지 않도록
정규화 후 포함 관계로 1차 판정하고, 최종 판정은 사람이 원문을 보고 확정했다.

## 3. 비용·시간의 해석 주의

- CLI는 OAuth로 인증돼 있다(`ANTHROPIC_API_KEY` 미설정). 따라서 `total_cost_usd`는
  **실청구액이 아니라 API 요율 환산 명목 비용**이다. 후보 간 상대 비교에는 유효하지만
  구독 요금제에서는 실제 과금과 다르다.
- `duration_ms`(API 소요)와 wall-clock을 분리해 기록했다. 차이는 **호출당 약 6.5초의
  CLI 기동 오버헤드**다. 이건 모델과 무관한 고정비이며, 영상 1편(생성 1회 + 검증 8회 = 9회)에
  약 58초가 순수 프로세스 기동으로 나간다. 배치 처리 시 이 값이 지배적이 되므로
  #9 구현 시 호출 횟수를 줄이는 설계가 필요하다.
- 표본이 후보당 생성 3회로 작다. 소수점 아래 차이를 신뢰하지 말 것.

## 4. 결과

### 4.1 생성 품질 — 실제로 갈린 유일한 축

후보별 3회 실행에서 나온 문제 12개씩, 총 36문제 전문은 `results.json`에 있다.

| 후보 | 회차 간 주제 반복 | 난이도 보정 | 평가 |
| --- | --- | --- | --- |
| `opus` | 낮음 — 세종대왕/제주도가 2회씩 재등장 | 양호 — hard에 광혜원(1885), 경국대전 반포왕, 노벨상 최신 부문 | **채택** |
| `sonnet` | **심각** — "물의 화학식"·"세종대왕이 창제한 문자" 각 3/3회 | 불량 — hard가 "노벨문학상 받은 최초 한국인", "태양계에서 가장 큰 행성" | 탈락 |
| `haiku` | 낮음 — 3회 모두 다른 주제군 | 양호 — hard에 676년 삼국통일, 직지심체요절 | 차선 |

`sonnet`의 반복은 프롬프트가 회차 간 다양성을 요구하지 않았기 때문일 수 있다. 다만 동일
조건에서 `opus`·`haiku`는 반복하지 않았으므로 모델 간 차이로 본다. 프롬프트 보강으로
완화 가능한지는 #9에서 확인할 여지가 있다.

### 4.2 정답 정확도 (사람 확인)

36문제 전수를 검토했다.

| 후보 | 명백한 정답 | 논란 소지 | 오답 |
| --- | --- | --- | --- |
| `opus` | 12 / 12 | 0 | 0 |
| `sonnet` | 12 / 12 | 0 | 0 |
| `haiku` | 11 / 12 | 1 | 0 |

`haiku`의 논란 소지 1건: **"한국 최초의 금속활자본 인쇄물은?" → "직지심체요절"**.
직지(1377)는 *현존하는* 최초이고, 기록상 최초는 상정고금예문(1234)이다. 질문에
"현존하는"이 빠져 있어 엄밀히는 답이 갈린다. **정답 자체가 틀린 게 아니라 질문 표현이
모호한 유형**이다.

블라인드 검증 결과 — 검증은 각 후보의 1회차 문제 4개, 문제당 2회, 총 24회.

| 후보 | 재답변 일치 | 스키마 성공 |
| --- | --- | --- |
| `opus` | 8 / 8 | 8 / 8 |
| `sonnet` | 8 / 8 | 8 / 8 |
| `haiku` | 8 / 8 | 8 / 8 |

**24/24 전원 일치 — 검증이 후보를 전혀 변별하지 못했다.** 두 가지를 뜻한다.

1. 생성된 문제가 대체로 쉬워서 검증기를 시험하지 못했다. 검증의 실효 검출률은
   **입증되지도 반증되지도 않았다.**
2. 위 `haiku`의 모호한 질문은 1회차가 아니라 3회차에 나와 검증 대상이 아니었다. 다만 이 유형은
   *정답이 틀린 게 아니라 질문이 모호한* 경우이므로, 블라인드 재답변으로는 원리상 잡히지 않는다.
   재답변 모델도 같은 근거로 "직지심체요절"이라 답할 것이기 때문이다.

### 4.3 구조화 출력(JSON) 실패율

| 후보 | 생성 | 검증 | 실패율 |
| --- | --- | --- | --- |
| `opus` | 3 / 3 | 8 / 8 | 0% |
| `sonnet` | 3 / 3 | 8 / 8 | 0% |
| `haiku` | 3 / 3 | 8 / 8 | 0% |

**`--json-schema`를 쓰면 이 축은 변별력이 없다.** CLI가 스키마를 강제하므로 모델 급과 무관하게
성공한다. 파이프라인에서 JSON 파싱 실패 재시도 로직을 미리 만들 필요가 없다는 뜻이기도 하다.
(단, 표본 33회로는 드문 실패를 배제하지 못한다. #9에서 실패 경로는 남겨 둘 것.)

### 4.4 비용·소요 시간

문제 1개당 = (생성 1회 ÷ 4문제) + (블라인드 검증 2회). 평균값.

| 후보 | 생성 1회 | 검증 1회 | **문제당 비용** | **문제당 API** | **문제당 wall** |
| --- | --- | --- | --- | --- | --- |
| `opus` | $0.0373 / 23.7s | $0.0068 / 3.2s | **$0.0229** | 12.4s | 26.9s |
| `sonnet` | $0.0240 / 13.4s | $0.0042 / 2.8s | **$0.0144** | 8.9s | 23.3s |
| `haiku` | $0.0206 / 23.6s | $0.0033 / 3.2s | **$0.0118** | 12.3s | 27.0s |

읽을 점 세 가지.

- **비용 격차가 정가 비율보다 훨씬 좁다.** opus:haiku 정가는 5배지만 실측은 1.9배다.
  호출이 짧아서 시스템 프롬프트·스키마 같은 고정 입력이 비용을 지배하기 때문이다.
  즉 이 워크로드에서 저가 모델로 내려가도 기대만큼 절약되지 않는다.
- **`haiku`가 `sonnet`보다 느렸다** (생성 23.6s vs 13.4s). 표본 3회라 단정할 수 없지만,
  최소한 "haiku = 빠름"을 전제로 설계하면 안 된다.
- **검증이 문제당 비용의 상당분을 차지한다.** opus 기준 $0.0136으로 문제당 비용의 59%다.
  그런데 4.2에서 보듯 검출 실적은 0이다. 이 비용의 정당성은 #10에서 재평가해야 한다.

## 5. provider 인터페이스 스케치

`#6`의 config 키와 `#9`·`#10`의 호출 지점을 정하기 위한 형태다. **구현은 이 스파이크의 범위가 아니다.**

```python
# src/llm/provider.py (예정)

from typing import Protocol
from dataclasses import dataclass

@dataclass(frozen=True)
class LLMResult:
    data: dict          # 스키마 검증을 통과한 파싱 결과
    raw: str            # 원문 (디버깅·감사용)
    model: str          # 실제로 응답한 모델 ID (별칭이 아니라 해석된 값)
    cost_usd: float | None   # provider가 보고하지 않으면 None
    latency_ms: int

class LLMProvider(Protocol):
    name: str

    def complete_json(self, *, system: str, prompt: str, schema: dict) -> LLMResult:
        """스키마를 만족하는 JSON을 반환한다. 실패 시 LLMError를 던진다."""
```

설계 판단 두 가지.

- **JSON 전용 메서드 하나만 둔다.** 자유 텍스트용 `complete_text()`를 지금 만들지 않는다.
  #9(퀴즈 생성)와 #10(블라인드 검증)이 둘 다 구조화 출력을 요구하므로, JSON을 유일한
  진입점으로 두면 모든 adapter가 스키마 강제를 각자 해결하게 강제된다. 자유 텍스트가
  실제로 필요한 타입이 생기면 그때 추가한다.
- **`cost_usd`를 `None` 허용으로 둔다.** claude CLI는 비용을 보고하지만 Ollama 같은 로컬
  실행은 보고할 것이 없다. 이 필드를 필수로 만들면 로컬 provider adapter가 거짓말을 하게 된다.

adapter는 `ClaudeCliProvider`(MVP), 이후 `AnthropicApiProvider` / `OpenAiProvider` /
`OllamaProvider`. **`ClaudeCliProvider`는 2.1의 격리 플래그를 내부에 고정으로 넣는다** —
호출자가 잊을 수 있는 성질의 것이 아니다.

### 5.1 #6 config 키 구조 제안

```yaml
llm:
  # 생성과 검증을 분리한다. 같은 모델로 블라인드 재답변을 시키면 프롬프트만 탈상관되고
  # 모델의 지식은 그대로 공유되므로 검증력이 구조적으로 약하다 (4.2).
  generator:
    provider: claude_cli
    model: opus
  verifier:
    provider: claude_cli
    model: opus          # 다른 모델/vendor로 바꿀 수 있게 키를 열어 둔다
    runs: 2              # 블라인드 재답변 횟수
    confidence_threshold: 0.8   # 미만이면 flagged (퀴즈 스펙 10장 미해결 항목)

  timeout_sec: 600
  max_retries: 2

  providers:
    claude_cli:
      binary: claude
    anthropic_api:
      api_key_env: ANTHROPIC_API_KEY
    ollama:
      base_url: http://localhost:11434
```

`generator`/`verifier`를 분리한 것이 핵심이다. 지금은 둘 다 `opus`지만, #10에서
검증 모델을 바꿔 실측하려면 키가 미리 열려 있어야 한다.
