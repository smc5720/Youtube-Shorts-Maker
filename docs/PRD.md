# YouTube Shorts Maker PRD

## 1. 개요

YouTube Shorts Maker는 사용자가 입력한 주제, 긴 원문, 기사 전문, 링크를 바탕으로 세로형 쇼츠 초안을 자동 생성하고, 사용자가 앱에서 직접 편집해 최종 영상을 내보낼 수 있는 로컬 우선 영상 제작 도구다. 1차 목표는 업로드 자동화가 아니라, 검수와 편집이 가능한 `1080x1920` MP4 쇼츠 파일을 안정적으로 생성하는 것이다.

초기 버전은 완전 자동 게시 시스템이 아니라 제작 보조 앱으로 설계한다. 대본, 음성, 자막, 영상 합성 결과물을 파일로 남기고, 사용자가 편집 화면에서 내용을 조정한 뒤 업로드 전에 확인할 수 있게 한다.

## 2. 목표

- 주제, 원문, 기사 전문, 링크 중 하나를 입력하면 쇼츠 영상 생성에 필요한 대본, 음성, 자막, 메타데이터, 최종 MP4를 생성한다.
- 결과물은 YouTube Shorts에 적합한 세로형 영상으로 출력한다.
- 각 생성 단계를 파일로 남겨 재실행, 검수, 수정이 가능하게 한다.
- 사용자가 생성된 초안을 앱에서 직접 편집할 수 있게 한다.
- 세로형 쇼츠 편집에 필요한 자막, 텍스트, 배경, 컷, 오디오 조정 기능을 제공한다.
- 저작권 리스크가 낮은 소스만 사용하도록 구조를 만든다.
- YouTube 업로드 자동화는 MVP 이후 단계로 분리한다.

## 3. 비목표

- MVP에서 YouTube 자동 업로드를 구현하지 않는다.
- MVP에서 트렌드 크롤링, 뉴스 수집, 대량 예약 생성은 구현하지 않는다.
- MVP에서 복잡한 멀티트랙 전문 편집기를 만들지 않는다.
- 타인의 YouTube 영상을 무단 다운로드해 재가공하는 기능은 기본 기능으로 제공하지 않는다.
- 수익화 최적화, 조회수 예측, 채널 운영 자동화는 초기 범위에 포함하지 않는다.

## 4. 대상 사용자

- 반복적으로 쇼츠를 제작하는 개인 크리에이터
- 교육, 정보, 요약형 콘텐츠를 제작하는 운영자
- 자동화 파이프라인을 직접 수정하고 싶은 개발자

## 5. 핵심 사용 시나리오

1. 사용자가 주제, 기사 전문, 긴 원문, 또는 링크를 입력한다.
2. 시스템이 입력 유형을 감지하고 원문 텍스트를 확보한다.
3. 링크 입력이면 페이지 본문을 추출하고 출처 URL을 기록한다.
4. 시스템이 원문에서 핵심 주장, 사실, 숫자, 인용 후보를 요약한다.
5. 시스템이 45~60초 분량의 쇼츠 대본을 생성한다.
6. 대본을 장면 단위로 나누고 각 장면에 필요한 시각 자료 설명을 만든다.
7. 대본을 TTS 음성으로 변환한다.
8. 음성 기준으로 자막 파일을 생성한다.
9. 배경 이미지나 영상을 세로형 캔버스에 배치한다.
10. 음성, 자막, 배경, 간단한 모션을 합성해 MP4를 만든다.
11. 앱에서 미리보기, 자막 수정, 텍스트 위치 조정, 배경 교체, 컷 순서 조정을 수행한다.
12. 제목, 설명, 태그 후보, 출처 정보를 `metadata.json`으로 저장한다.
13. 사용자가 최종 MP4를 내보낸 뒤 직접 업로드한다.

## 6. MVP 범위

### 6.1 입력

- CLI 인자: `--topic "주제"`, `--url "https://..."`, `--text-file input/source.txt`
- 선택 입력 파일: `input/topic.txt`, `input/source.txt`, `input/urls.txt`
- 선택 설정 파일: `config.yaml`

### 6.2 출력

```text
outputs/
  run-{timestamp}/
    scenes.json          # 공통
    audio/
      seg-000.mp3        # 공통 — 낭독 장면별 세그먼트
      seg-002.mp3
      segments.json      # 공통 — 세그먼트를 만든 텍스트의 기록 (재실행용)
    voice.mp3            # 공통 — 세그먼트를 타임라인에 배치한 합성 트랙
    captions.srt         # 공통
    metadata.json        # 공통
    project.json         # 공통
    final_short.mp4      # 공통
    quiz.json            # 타입 전용 (quiz)
    source.json          # 입력 경로 전용 — --url / --text-file
    summary.json         # 입력 경로 전용 — 원문 요약이 있을 때만
    script.txt           # 타입 전용 (내레이션 대본을 쓰는 타입)
```

**모든 파일이 항상 생성되는 것은 아니다.** 산출물은 세 부류로 나뉜다.

| 파일 | 구분 | 생성 조건 |
| --- | --- | --- |
| `scenes.json` | 공통 | 항상 |
| `audio/seg-*.mp3` | 공통 | `narrate: true` 장면이 있을 때, 그 장면 수만큼 |
| `audio/segments.json` | 공통 | 세그먼트가 1개 이상일 때. **계약 파일이 아니다** — 재실행이 무엇을 다시 쓸지 판단하는 이 단계의 기록이며(7.5.2), 지우면 다음 실행이 전부 다시 합성한다 |
| `voice.mp3` | 공통 | 세그먼트가 1개 이상일 때 |
| `captions.srt` | 공통 | 항상 |
| `metadata.json` | 공통 | 항상 |
| `project.json` | 공통 | 항상 |
| `final_short.mp4` | 공통 | 렌더 성공 시 |
| `quiz.json` | 타입 전용 (`quiz`) | `--type quiz` |
| `script.txt` | 타입 전용 | 내레이션 대본을 쓰는 타입만. **퀴즈 타입은 생성하지 않는다** — 퀴즈의 낭독 대상은 `quiz.json`의 질문·정답 필드이며 별도 대본이 없다 |
| `summary.json` | 입력 경로 전용 | 원문 요약(7.2)을 거칠 때만. **`--topic` 입력과 퀴즈 타입은 생성하지 않는다** |
| `source.json` | 입력 경로 전용 | `--url` 또는 `--text-file` 입력일 때만. **`--topic` 입력은 생성하지 않는다** |

`script.txt` / `summary.json` / `source.json`이 없는 것은 실패가 아니다. 후속 단계는 이 세
파일의 존재를 전제하지 않는다.

### 6.3 영상 규격

## 7. 기능 요구사항

### 7.1 입력 수집

- 입력은 짧은 주제, 긴 원문, 기사 전문, 링크를 모두 지원한다.
- 링크 입력은 MVP에서 단일 URL을 우선 지원한다.
- 링크에서 추출한 본문, 제목, URL, 접근 시각을 `source.json`으로 저장한다.
- 원문 직접 입력은 입력 파일 경로와 텍스트 길이를 `source.json`으로 저장한다.
- 본문 추출 실패 시 사용자에게 직접 원문 입력을 요구할 수 있도록 실패 사유를 남긴다.

### 7.2 원문 요약

- 긴 원문은 바로 쇼츠 대본으로 변환하지 않고 먼저 요약한다.
- 핵심 주장, 배경 맥락, 중요한 숫자, 고유명사, 주의해야 할 불확실성을 분리한다.
- 출처가 있는 경우 메타데이터와 설명에 포함할 출처 후보를 만든다.
- 결과를 `summary.json`으로 저장한다.

### 7.3 대본 생성

- 입력 주제 또는 요약된 원문에서 쇼츠용 내레이션 대본을 생성한다.
- 첫 3초에 후킹 문장을 포함한다.
- 문장은 TTS와 자막에 적합하도록 짧게 작성한다.
- 과장, 허위 사실, 검증 불가 주장을 줄이는 프롬프트를 사용한다.
- 원문 기반 콘텐츠는 원문에 없는 사실을 임의로 추가하지 않는다.
- 결과를 `script.txt`로 저장한다.

### 7.4 장면 분할

- 대본을 3~6개 장면으로 나눈다.
- 각 장면은 내레이션 텍스트, 예상 길이, 시각 자료 설명을 가진다.
- 결과를 `scenes.json`으로 저장한다.
- 이 단계에서 넣는 길이는 **예상값**이다. 최종 길이는 7.5.1 규칙으로 확정한다.

#### 7.4.1 `scenes.json` 단일 계약

`scenes.json`은 콘텐츠 산출물과 공통 파이프라인 사이의 **유일한 계약**이다.

- TTS(7.5), 자막(7.6), 렌더러(7.7), 메타데이터(7.8)는 `scenes.json`만 읽는다.
- 이 네 모듈은 `quiz.json` 같은 타입 전용 산출물을 **직접 참조하지 않는다**. 타입 전용 정보가
  렌더에 필요하면 장면 템플릿이 `scenes.json` 필드로 옮겨 담는다.
- 타입 전용 렌더 요소(퀴즈의 카운트다운, 정답 강조)도 `scenes.json`의 `role`과 필드로만
  구분한다. 렌더러는 `role`을 보고 분기하되, 그 `role`이 어떤 콘텐츠에서 나왔는지는 모른다.

이 경계가 깨지면 두 번째 쇼츠 타입을 추가할 때 공통 파이프라인 전체를 고쳐야 한다.
상세는 [퀴즈 스펙 1장](types/quiz.md#1-타입-플러그인-개념).

### 7.5 음성 생성

- MVP 기본값은 무료 또는 로컬 실행이 쉬운 TTS provider를 사용한다. **Edge TTS, 기본 음성
  `ko-KR-SunHiNeural`로 확정됐다 (14.1 참조).**
- provider는 교체 가능하게 설계한다. 단어 타이밍 제공 여부는 provider마다 다르므로
  필수가 아닌 선택 기능으로 둔다.
- 낭독 장면마다 세그먼트 오디오를 만들고, 이를 타임라인에 배치한 합성 트랙을 `voice.mp3`로 저장한다 (7.5.2).
- **provider는 길이를 보고하지 않는다.** 합성 결과 파일을 공통 코드가
  `ffprobe format=duration`으로 재고, 그 값이 7.5.1의 입력이다. provider마다 보고 정확도가
  다르므로 계약에 길이 칸을 두면 adapter가 거짓말할 자리가 생긴다. 따라서 채택 조건은
  "길이를 보고할 수 있는가"가 아니라 **"합성 결과가 결정적인가"**다 — 재합성 길이가 흔들리면
  캐시 적중과 미적중이 다른 영상을 만든다 (14.1 "TTS 길이 확정과 세그먼트 캐시").

#### 7.5.1 타이밍 확정 규칙 — duration은 실측 오디오 길이로 정한다

**스펙과 장면 템플릿에 적힌 초 단위 값은 목표치이며 최종 길이가 아니다.** TTS 낭독 길이는
문장마다 다르므로, 목표치를 그대로 `duration`으로 쓰면 자막·오버레이·효과음이 음성과 어긋난다.

낭독이 있는 장면(`narrate: true`)의 길이는 아래로 확정한다.

```text
duration = max(
    lead_in + measured_audio_duration + tail,
    min_duration,
    caption_onset + len(caption) / reading_cps + tail    # `caption`이 있는 장면만
)
```

| 값 | 기준값 | config 키 | 근거 |
| --- | --- | --- | --- |
| `lead_in` | 0.30초 | `timing.lead_in_sec` | 장면 전환 직후 바로 말이 시작되면 앞부분이 묻힌다 |
| `tail` | 0.50초 | `timing.tail_sec` | 낭독이 끝난 프레임에서 컷하면 화면 텍스트를 읽을 시간이 없다. 정답 강조 애니메이션이 끝날 여유도 여기서 확보한다 |
| `min_duration` | 1.20초 | `timing.min_duration_sec` | "나일강"처럼 짧은 낭독이 눈에 안 들어올 만큼 짧은 컷이 되는 것을 막는다 |
| `caption_onset` | 0.90초 | `timing.caption_onset_sec` | 화면에 해설 자막이 뜨는 시각. 정답 강조가 끝난 뒤에 뜬다 (D1 확정 스펙 5.4). 렌더러(#22)와 이 공식이 **같은 값을 읽는다** |
| `reading_cps` | 12.0 | `timing.reading_cps` | 한국어 자막의 초당 읽기 글자 수 |

**세 번째 항이 자막 읽기 하한이다.** 낭독이 없는 해설은 자막이 유일한 전달 경로인데
(퀴즈 스펙 0장), 정답 낭독은 2초면 끝나고 `min_duration` 1.20초는 한국어에서 한 번도 걸리지
않아 해설을 읽을 시간을 아무것도 보장하지 못한다. **`role`이 아니라 `caption` 필드의 존재로
분기한다** — 다른 타입이 같은 필드를 쓰면 같은 보장을 얻는다 (7.4.1).

- `measured_audio_duration`은 **합성된 파일을 실제로 측정한 값**이다. provider가 예측한 값이나
  글자 수 추정치를 쓰지 않는다.
- 확정된 값은 소수 3자리(밀리초)로 반올림해 `scenes.json`에 기록한다. 30fps 프레임 경계 정렬은
  렌더러가 처리하고, `scenes.json`에는 초 단위 실수를 그대로 둔다.
- 장면 템플릿이 넣은 목표치는 **검증용 기준으로만 남긴다.** 실측 확정값이 목표치의 2배를 넘거나
  절반 미만이면 경고를 남긴다 — 프롬프트가 너무 긴 문장을 만들었거나 합성이 실패한 신호다.
- 전체 영상 길이는 확정된 `duration`의 합이다. 6.3의 45~60초는 목표 범위이며, 합이 이 범위를
  벗어나면 경고를 남기되 렌더를 막지 않는다.

**낭독이 없는 장면은 고정 길이를 쓴다.** 실측할 오디오가 없으므로 위 규칙을 적용하지 않는다.
현재 정의된 고정 길이 장면은 다음과 같다.

| `role` | 길이 결정 | 비고 |
| --- | --- | --- |
| `countdown` | `quiz.json`의 `countdown_sec` (기본 3초) | 비프음은 있지만 낭독이 아니다. 숫자 전환 시점이 정수 초에 맞아야 하므로 실측 보정 대상이 아니다 |
| `hook` | 고정 2.5초 | 현 퀴즈 스펙의 TTS 범위가 질문·정답뿐이라 낭독이 없다 |
| `cta` | 고정 3.0초 | 위와 같다 |

세 값은 **D1 영상 디자인 시안이 그 길이로 프레임 레이아웃을 검증했기 때문에** 그 쪽으로
맞춘 것이다 (각각 3.0 / 4초 / 4.0에서 변경). 근거와 새 길이 예산은
[D1 확정 스펙 3장](design/d1-video-design-spec.md).

`hook` / `cta`에 낭독을 추가하기로 결정하면 두 장면은 이 표에서 빠지고 실측 규칙을 따른다.
그때 바꿔야 하는 것은 `narrate` 플래그뿐이다 — 규칙은 `narrate`로 분기하므로 고정 길이 목록을
코드에 하드코딩하지 않는다.

#### 7.5.2 오디오 산출물 규격

세그먼트 오디오와 합성 트랙을 모두 남긴다. 세그먼트는 재합성 없이 개별 교체·재생성이 가능해야
하고, 합성 트랙은 렌더러가 단일 입력으로 받아야 한다.

```text
outputs/run-{timestamp}/
  audio/
    seg-000.mp3     # scenes[0]이 낭독 장면일 때
    seg-002.mp3     # scenes[2]
  voice.mp3         # 전체 타임라인 길이의 단일 트랙
```

- **명명**: `audio/seg-{scene_index:03d}.mp3`. `scene_index`는 `scenes.json`의 `scenes` 배열
  인덱스(0-based)다. 낭독 장면이 아닌 인덱스는 건너뛰므로 번호가 연속하지 않는다.
  파일명에 `question`·`answer` 같은 타입 전용 어휘를 넣지 않는다 — 7.4.1 경계를 지키기 위함이다.
- **개수**: `narrate: true`인 장면 수와 같다.
- **합성 트랙**: `voice.mp3`는 확정된 전체 길이를 가지며, 각 세그먼트를
  `scene_start + lead_in` 위치에 배치하고 나머지 구간은 무음으로 채운다. 효과음과 배경음악은
  섞지 않는다 — 렌더 단계에서 별도 트랙으로 믹싱한다.
- **`scenes.json`에 기록하는 필드**: 각 낭독 장면에 세그먼트 파일 경로(`audio`), 실측 오디오
  길이(`audio_duration`), 합성 트랙 내 낭독 시작 오프셋(`narration_offset`)을 남긴다. 자막(7.6)은
  이 오프셋을 기준으로 타임코드를 만든다. **이 세 이름으로 확정됐다** — 스키마 정의는
  `src/shorts_maker/schemas/scenes.py`이고, 세 필드는 `narrate: true` 장면에만 존재한다.
  파일명은 같은 모듈의 `segment_path(scene_index)`가 만든다.
- **재실행**: 같은 `(provider, voice, 원문 텍스트)`의 합성 결과는 run 디렉터리 **밖**의
  캐시(`tts.cache_dir`, 기본 `.cache/tts`)에 오디오와 사이드카 JSON(실측 길이, 단어 타이밍)으로
  남고, 다음 실행은 합성 없이 그것을 세그먼트 경로로 복사한다. **캐시를 run 디렉터리 안에
  두지 않는다** — run마다 새 디렉터리이므로 반복 실행 비용이 줄지 않는다(13장). 적중 시
  길이를 다시 재지 않는 것은 사이드카의 값이 같은 바이트를 잰 결과이기 때문이다.
  `tts.cache_dir: null`이면 캐시를 끄고 매번 합성한다.
- **같은 run 디렉터리 재실행**: 위 캐시와 별개로, run 디렉터리 안에 이미 있는 세그먼트를
  그대로 쓴다. 판단 기준은 `audio/segments.json`에 남긴 `(provider, voice, 텍스트)`이고,
  일치하면 합성하지 않되 **`audio_duration`은 그 파일을 다시 재서** 채운다 — 세그먼트는
  사람이 개별 교체할 수 있는 파일이므로 기록된 길이가 아니라 디스크에 있는 것이 진실이다.
  캐시는 run 사이에 합성을 아끼는 층이고, 이 재사용은 한 run 디렉터리 안에서 사람이 손댄
  파일을 지키는 층이다. `text`를 고치고 다시 실행하면 그 장면만 다시 합성된다.

### 7.6 자막 생성

- MVP에서는 음성 길이와 대본 문장 기준으로 SRT를 생성한다.
- 타임코드는 `scenes.json`의 확정된 `duration`과 낭독 시작 오프셋(7.5.2)에서 계산한다.
  장면 템플릿의 목표치를 기준으로 계산하지 않는다. 입력이 확정 상태인지는 자막 단계가
  입구에서 다시 확인한다 (`validate_scenes_final`).
- 낭독이 없는 장면(`hook`, `cta`, `countdown`)의 자막은 장면 구간 전체를 덮는다.
- 이후 Whisper 또는 Faster Whisper 기반 word-level timestamp로 개선한다.
- 결과를 `captions.srt`로 저장한다.

**큐는 장면당 하나다.** `text`와 `caption`이 둘 다 있는 장면(정답)에서도 큐를 나누지 않고
한 큐 안에 두 문구를 담는다. SRT는 단일 트랙이라 두 큐가 겹칠 수 없으므로, 나누면 해설이
장면 구간 밖으로 밀리거나 정답 자막이 화면(7.7의 번인)보다 일찍 사라진다. 문구가 없는
장면(`countdown`)은 큐를 만들지 않는다.

| 장면 | 큐 시작 | 큐 끝 |
| --- | --- | --- |
| `narrate: true` | `narration_offset` | 장면 끝 |
| 낭독 없음 | 장면 시작 | 장면 끝 |

**줄바꿈은 두 층이다.** `captions.max_chars_per_line`(기본 18) / `captions.max_lines`
(기본 4)는 외부 재생기가 여는 SRT 트랙의 값이고, 화면 번인의 줄바꿈은 이 값을 쓰지 않는다 —
번인은 `drawtext` 인스턴스마다 폰트 크기가 달라 줄당 글자 수가 요소별로 갈리며, 렌더러가
`floor(840 / font_size)`로 계산한다 (D1 확정 스펙 1장·5장). SRT에는 폰트 크기라는 개념이
없으므로 트랙 전체에 하나의 값을 쓴다.

줄바꿈은 어절 단위이고, 한 어절이 한 줄 상한을 넘을 때만 그 어절 안에서 자른다. **줄 수
상한을 넘으면 자르지 않고 경고한다** — 원문을 잃는 쪽이 더 나쁘고, 조정 대상은 자막이
아니라 문장 길이나 상한값이다.

### 7.7 영상 합성

- FFmpeg를 기본 렌더링 엔진으로 사용한다.
- 배경 이미지 또는 영상을 `1080x1920` 캔버스에 맞춘다. **비율을 유지한 채 넘치는 쪽을
  잘라 채운다** — 빈 영역을 남기지 않는다.
- 자막은 모바일에서 읽기 쉬운 크기와 위치로 번인한다.
- 장면 전환은 MVP에서 단순 컷 또는 약한 zoom/pan만 사용한다.
- 오디오 스트림은 **낭독이 없어도 항상 정확히 하나**다. 낭독 장면이 없는 입력에서는 무음
  트랙을 넣는다 — 효과음을 얹는 단계(#23)가 스트림 하나를 전제할 수 있어야 한다.

#### 효과음 믹싱 (#23)

효과음은 **렌더 패스 안에서** 낭독 트랙 위에 얹는다. 중간 파일을 만들지 않으므로 6.2의
산출물 목록이 늘지 않고, 믹스 결과는 계속 스트림 하나다.

- 트리거 시각은 `scenes.json`의 `sfx`와 장면의 프레임 구간에서 나온다 — 카운트다운은 숫자가
  갈리는 프레임마다, 정답은 정답이 등장하는 순간 한 번이다. **그림과 같은 프레임 계산을
  쓴다** (`overlay.countdown_windows` / `overlay.ANSWER_ONSET_SEC`).
- 레벨은 `project.json`의 `audio.sfx_volume`(선형 게인)이 정한다. 번들 효과음이 낭독보다
  peak 9.5dB / RMS 9~10dB 아래로 정규화돼 있어(#18) 기본값 1.0에서 추가 감쇠가 없다.
- 믹스 끝에 리미터를 둬서 최종 오디오가 **-1 dBFS**를 넘지 않는다. 기본 설정에서는 걸리지
  않고, 사람이 게인을 올렸거나 낭독 레벨이 다른 provider를 쓸 때만 동작한다.
- 게인이 `0`이거나 `sfx`가 하나도 없으면 효과음 입력과 믹스 필터를 만들지 않는다 — 그때의
  명령은 #22까지의 것과 같다.

#### 프레임 경계 정렬 (#19)

`duration`은 밀리초 자리 실수이고 30fps 한 프레임은 33.33ms라, 정렬 규칙이 없으면 장면
경계가 프레임 사이에 떨어진다. 규칙은 아래 하나이고 **`video_renderer.align()` 함수 하나가
소유한다.**

```text
frames_i     = round(duration_i * fps)
start_i      = sum(frames_0..i-1) / fps
total_frames = sum(frames_i)
```

- 오버레이(#20~#22)가 `enable='between(t,a,b)'`에 쓸 장면 시작 시각을 각자 `duration`으로
  다시 누적하면 요소마다 다른 경계를 갖게 된다. 그 값은 이 함수에서만 받는다.
- 영상 총 길이는 `total_frames / fps`다. `voice.mp3`의 길이(`sum(duration)`)와 최대 반
  프레임 차이가 나므로 오디오를 무음으로 패딩한다.

### 7.8 메타데이터 생성

- 제목 후보 3개, 설명, 태그 후보를 생성한다.
- 링크나 원문 기반 콘텐츠는 출처 URL 또는 원문 출처 정보를 포함한다.
- 결과를 `metadata.json`으로 저장한다.
- 업로드는 하지 않는다.

**필드는 아래로 확정됐다.** 스키마 정의는 `src/shorts_maker/schemas/metadata.py`에 있고,
생성은 `metadata_generator`가 LLM 호출 1회로 한다 (#13).

```json
{
  "schema_version": 1,
  "type": "quiz",
  "language": "ko",
  "titles": [
    "이 상식 4개, 다 맞히면 상위 1%",
    "상식 퀴즈 4문제, 몇 개 맞히나요",
    "세계 지리 상식 테스트"
  ],
  "description": "세계 지리 상식 퀴즈 4문제입니다. 정답을 맞혀 보세요.",
  "tags": ["상식퀴즈", "지리"],
  "source": null
}
```

| 필드 | 의미 |
| --- | --- |
| `titles` | 업로드 시 고를 제목 후보. **정확히 3개**를 스키마가 강제한다 — 사람이 셋 중 하나를 골라 붙여넣는 것이 용도이므로 개수가 계약이다 |
| `description` | 업로드 설명문 |
| `tags` | 태그 후보. 1개 이상이며 상한은 `metadata.tag_max_count` |
| `source` | 출처 URL 또는 원문 출처 표기. **nullable 필수 필드다** — 필드를 통째로 빼면 "출처가 없는 입력 경로였다"와 "생성기가 빠뜨렸다"가 구분되지 않는다 |

- **입력은 `scenes.json`뿐이다** (7.4.1). 제목의 재료는 장면의 `role` / `text` / `caption`이며,
  `quiz.json` 같은 타입 전용 산출물을 열지 않는다.
- **확정 상태를 요구하지 않는다.** 장면 초안만으로 생성한다 — 메타데이터는 오디오 길이와
  무관하고, 렌더가 실패해도 남아야 하는 산출물이다 (6.2 표).
- 제목 길이와 태그 개수의 상한은 config가 정한다 (`metadata.title_max_len` 기본 40,
  `metadata.tag_max_count` 기본 10). YouTube의 하드 리밋(제목 100자)이 아니라 모바일 검색
  결과에서 잘리지 않게 하려는 운영 기준이므로 config에 둔다.
- `--topic` 입력에는 출처가 없어 `source`가 `null`이다. `--url` / `--text-file` 경로에서
  값을 채우는 것은 #31이다.

### 7.9 편집 앱

- 사용자는 생성된 프로젝트를 앱에서 열 수 있다.
- 앱은 세로형 캔버스 미리보기를 제공한다.
- 앱은 장면 목록을 보여주고, 장면별 텍스트, 자막, 배경, 길이를 수정할 수 있게 한다.
- 편집 내용은 프로젝트 파일로 저장한다.
- 미리보기 렌더링은 빠른 프리뷰와 최종 렌더링을 분리한다.
  - **프레임마다 FFmpeg를 새로 띄우는 방식은 성립하지 않는다.** 프리뷰 1프레임이 0.8~2.4초이고
    그 바닥이 프로세스 기동이라 해상도를 낮춰도 빨라지지 않는다 (스파이크 #25 6장, 14.1).
  - **장면 대표 프레임을 프로세스 하나로 전부 만들어 캐시에 넣는다** (`video_renderer.preview`,
    14.1). 11장면 실측 2.2초이고, 그 뒤 장면 이동은 3~5ms다.
  - 프리뷰 명령은 최종 렌더 명령에서 갈라져 나와야 한다. 다른 코드로 그리면 화면과 결과가
    갈릴 수 있고, 갈라지는 지점은 `video_renderer._video_stage` 하나다 — 배경과 오버레이를
    두 명령이 거기서 함께 받고, 뒤에서 갈리는 것은 오디오 유무와 인코더뿐이다.
- 프리뷰의 대기 표현은 두 가지다. **다른 장면을 고르면 이전 프레임을 지우고**(남기면 방금 고른
  장면의 그림으로 읽힌다), **같은 장면의 값이 바뀌면 이전 프레임을 유지한 채 갱신 표시를
  띄운다**(지우면 값 하나 고칠 때마다 비교할 대상이 사라진다).
- 최종 내보내기는 FFmpeg 렌더링 엔진을 사용한다.

### 7.10 프로젝트 파일

- 편집 가능한 상태는 `project.json`으로 저장한다.
- `project.json`은 장면, 자막, 텍스트 오버레이, 배경 소스, 오디오 소스, 렌더링 설정을 포함한다.
- 앱은 `project.json`을 기준으로 미리보기와 최종 렌더링을 수행한다.

**생성 직후의 초기 상태**는 아래로 확정됐다. 스키마 정의는
`src/shorts_maker/schemas/project.py`에 있다.

```json
{
  "schema_version": 1,
  "type": "quiz",
  "language": "ko",
  "scenes": "scenes.json",
  "background": { "kind": "preset", "value": "deep_navy" },
  "audio": { "voice": "voice.mp3", "music": null, "sfx_volume": 1.0 },
  "render": {
    "width": 1080, "height": 1920, "fps": 30, "output": "final_short.mp4",
    "caption_style": "impact_yellow", "font_path": null,
    "cta_punch": "구독 · 좋아요", "cta_tail": "매일 새 상식 퀴즈",
    "caption_onset_sec": 0.90,
    "scene_overrides": []
  },
  "review": { "acknowledged": [], "stale": [] }
}
```

| 필드 | 내용 |
| --- | --- |
| `scenes` | `scenes.json` 경로. **장면 배열을 복사하지 않는다** — 같은 장면이 두 곳에 있으면 어느 쪽이 원본인지 모호해진다 (7.4.1) |
| `background.kind` | `preset` \| `color` \| `image` \| `video`. `preset`은 번들 프리셋 이름, `color`는 색상 값, 나머지는 사용자 파일 경로 (14.1의 배경 소스 결정) |
| `audio.voice` | 합성 트랙 경로. 낭독 장면이 없으면 `voice.mp3`가 생성되지 않으므로 `null`이 될 수 있다 (6.2) |
| `audio.music` | 사용자가 라이선스를 확인한 파일만. 기본은 `null` (8장) |
| `audio.sfx_volume` | 효과음의 선형 게인. `config`의 `audio.sfx_volume`에서 오고 **렌더러가 읽는 유일한 자리다** (#23). `0`이면 효과음 없이 렌더한다. 앱이 붙일 트랙별 볼륨도 이 섹션에 온다 |
| `render` | 6.3의 영상 규격과 출력 파일명, 그리고 번인 오버레이가 읽는 값 — 자막 스타일·폰트 경로·cta 문구·`caption_onset_sec` |
| `render.caption_onset_sec` | 해설 자막이 뜨는 시각(장면 시작 기준 초). `timing.caption_onset_sec`에서 오고, **장면 길이 하한을 계산한 7.5.1의 공식이 읽은 값과 같은 값이다** — 렌더러가 상수를 갖거나 config를 다시 열면 화면과 길이 계산이 갈린다 |
| `render.scene_overrides` | 사람이 얹은 장면 편집 (#82, #83). 항목마다 `role` + `question_id`로 장면을 가리키고 `duration`(그리고 #83의 문구·오버레이)을 얹는다. **`scenes.json`을 덮지 않는다** — 낭독보다 짧은 `duration`은 확정 검증이 거부하므로 그쪽에 쓰면 앱의 저장이 실패한다 (14.1). **선택 필드다.** 키가 인덱스가 아닌 이유는 문제를 추가·삭제하면 인덱스가 밀려 조정한 값이 다른 장면에 붙기 때문이다 |
| `review` | **앱이 소유하는 편집 상태이고 렌더러가 읽지 않는 유일한 섹션이다** (#28). `acknowledged`는 사람이 `flagged`/`unverified`를 확인한 항목 번호, `stale`은 낭독 문구가 바뀌어 오디오·자막이 낡은 항목 번호. 둘 다 `scenes.json`의 `question_id`와 같은 값이고 중복을 허용하지 않는다. **선택 필드다** — 이 값이 생기기 전에 만들어진 run 디렉터리가 그대로 열려야 한다 |
| `review.timeline_stale` | 사람이 장면 길이를 고쳐 `captions.srt`·`voice.mp3`가 어긋난 상태 (#82). **목록이 아니라 참·거짓이다** — 길이 하나를 고치면 그 뒤 장면의 시작 시각이 전부 밀려 낡는 대상이 타임라인 전체다. 지우는 것은 `stale`과 같이 재생성(#77) |

- 경로 값은 모두 **run 디렉터리 기준 상대 경로**다. 디렉터리를 옮겨도 프로젝트가 열려야 한다.
- **초기 상태를 쓰는 것은 `project.py`이고, 렌더보다 먼저 쓴다** (#19). `project.json`은 항상
  생성되고 `final_short.mp4`는 렌더 성공 시에만 생성되므로(6.2 표), 렌더가 실패한 run에도
  값을 고쳐 다시 돌릴 파일이 남는다.
- **렌더러의 입력 계약이다.** 배경·오디오·출력 규격을 렌더러가 config에서 다시 읽지 않는다 —
  값을 정하는 경로가 둘이 되면 앱이 편집한 프로젝트와 CLI 렌더가 갈린다. `render.background`
  설정이 만드는 `background.kind`는 `preset` 하나이고, 나머지 세 종류는 사람이나 앱(#29)이
  이 파일을 편집해 넣는다.
- **편집 상태로 열린 것은 `review` 하나다** (#28). **앱이 쓰는 것과 편집 상태인 것은 다르다** —
  `render.scene_overrides`는 앱만 쓰지만 렌더러가 읽으므로 `render`에 있고 지문에도 들어간다
  (#82). **자막 스타일 선택도 편집 상태가 아니다**: 렌더러가 읽는 값이라
  `render.caption_style`이 이미 그 자리다. 트랙별 볼륨은 #81이 `audio`에 붙인다.
- **`review`가 렌더러가 읽지 않는 유일한 섹션이라는 사실에 프리뷰 캐시가 기댄다.**
  `schemas/project.py`의 `APP_STATE_SECTIONS`가 그 목록이고 `api._signature`가 지문에서
  뺀다 — 빼지 않으면 확인 버튼 한 번이 프레임 전부를 다시 만들고 결과는 같은 그림이다.
  목록이 "렌더가 읽는 것"이 아니라 **"렌더가 읽지 않는 것"** 쪽인 이유는, 새 섹션이
  아무것도 하지 않아도 지문에 들어가야 화면이 옛 그림에 머물지 않기 때문이다.

## 8. 안전장치 및 정책 고려

- 기본 소스는 사용자가 제공한 파일, 직접 생성한 에셋, 라이선스가 명확한 무료 소스만 사용한다.
  - **번들되는 에셋은 자체 생성을 우선한다.** 저장소에 커밋되는 파일은 clone과 앱 동봉까지
    재배포 범위가 넓어, 조건이 없는 자체 생성이 가장 위험이 작다. 효과음은 이 이유로
    FFmpeg 합성으로 만들었다 (`assets/sfx/CREDITS.md`, #18). 자체 생성이 어려운 종류
    (폰트·배경 등, #38)는 재배포와 앱 동봉을 허용하는 라이선스만 채택하고, 그 근거 문장과
    표기 문구를 에셋 디렉터리의 `CREDITS.md`에 남긴다.
  - **#38에서 세 종류가 들어왔다.** 폰트는 Pretendard(SIL OFL 1.1 — 동봉 재배포·임베딩 허용,
    라이선스 원문 동봉이 조건), 배경과 자막 스타일은 D1 확정 스펙에서 옮긴 이 저장소의
    정의값이라 조건이 없다. **Windows 동봉 폰트(`malgun.ttf`)에 의존하지 않는다** — 재배포가
    금지되어 저장소에도 앱에도 담을 수 없다.
- 링크 입력은 본문 요약과 변환 용도로 사용하되, 원문을 그대로 긴 분량 복제하지 않는다.
- 기사 기반 콘텐츠는 출처를 기록하고, 사실 여부가 중요한 내용은 검수 단계를 거친다.
- 업로드 자동화는 YouTube Data API v3 정책과 OAuth 설정을 별도 문서로 검토한 뒤 구현한다.
- 대량 생성/대량 업로드 기능은 기본값으로 제공하지 않는다.
- 생성된 대본과 메타데이터는 업로드 전 사람이 검수할 수 있어야 한다.
- 음악은 기본 제공하지 않거나, 사용자가 라이선스를 확인한 파일만 사용한다.

## 10. 제안 기술 스택

- 언어: Python 3.11+
- 앱: Electron + React — 백엔드는 앱이 자식 프로세스로 띄우고 stdio JSON Lines로 말한다 (14.1 참조)
- 렌더링 백엔드: Python 3.11+ — 앱 동봉은 PyInstaller onedir, FFmpeg는 동봉하지 않는다 (14.1 참조)
- CLI: argparse
- 설정: YAML
- 영상 처리: FFmpeg — 명령을 직접 생성한다 (MoviePy 미사용, 14.1 참조)
- 기본 배경: 단색/그라디언트 내장 + 사용자 파일 교체 (14.1 참조)
- 1차 언어: 한국어 — 스키마의 `language` 필드로 확장 여지 유지 (14.1 참조)
- LLM: 로컬 `claude` CLI 헤드리스 호출, 기본 모델 `claude-opus-5` — provider 방식으로 교체 가능하게 설계 (14.1 참조)
- TTS: Edge TTS, 기본 음성 `ko-KR-SunHiNeural` — provider 방식으로 교체 가능하게 설계 (14.1 참조)
  - 공식 승격 경로: Azure AI Speech (동일 음성 이름 제공)
  - 오프라인 승격 경로: MeloTTS-Korean (MIT). **Kokoro는 한국어 미지원으로 후보에서 제외**
- 자막: SRT, 이후 ASS 스타일 자막 지원
- 전사/정렬: Edge TTS의 WordBoundary가 단어 타이밍을 제공하므로 word-level timestamp에
  전사가 불필요할 수 있다 (14.1 참조). Faster Whisper는 TTS 외 입력이 생길 때 검토
- 업로드: MVP 이후 YouTube Data API v3 검토

## 13. 성공 기준

- 하나의 주제, 원문 파일, 또는 링크 입력으로 `final_short.mp4`가 생성된다.
- 생성 결과를 앱에서 열고 자막, 텍스트, 배경, 장면 순서를 수정할 수 있다.
- 편집 상태가 `project.json`으로 저장되고 다시 열 수 있다.
- 출력 영상은 `1080x1920`, H.264 MP4, 30fps로 렌더링된다.
- 원문 정보, 요약, 대본, 장면 정보, 음성, 자막, 메타데이터가 모두 저장된다.
- 같은 입력으로 실패 없이 반복 실행할 수 있다.
- 업로드 전 사람이 검수할 수 있는 산출물이 남는다.

## 14. 결정사항

### 14.1 확정된 결정

#### 렌더링 방식: FFmpeg 명령 직접 생성 (MoviePy 미사용)

MVP는 MoviePy를 쓰지 않고 FFmpeg 명령을 직접 생성한다.

근거 — 퀴즈 타입은 프레임 단위 타이밍 제어(카운트다운 진행, 정답 등장 시점)가 핵심이고,
`drawtext`의 시간 표현식으로 직접 제어하는 편이 MoviePy 추상화보다 정확하다. 이 저장소에서
`fontsize`가 시간 표현식(`T` 플래그)을 받는 것이 실제 렌더로 확인됐으므로, 정답 강조
스케일 애니메이션에 PNG 시퀀스 사전 렌더링이나 별도 라이브러리가 필요하지 않다.

영향 — 10장(기술 스택), 렌더링 이슈 #19~#24의 완료 조건.

#### 기본 배경 소스: 단색/그라디언트 기본 제공 + 사용자 파일 교체

MVP는 단색과 그라디언트 배경을 기본 제공하고, 사용자가 자신의 이미지/영상 파일로 교체할 수
있게 한다. 무료 이미지 API 연동은 MVP 이후로 미룬다.

근거 — 8장 라이선스 정책 리스크를 최소화한다. 외부 API 소스는 라이선스 조건과 출처 표기
요구가 제공자마다 달라 검증 부담이 크고, 퀴즈 타입은 텍스트 가독성이 우선이라 복잡한 배경의
이득이 작다.

영향 — `project.json`의 배경 필드(#7), 배경 프리셋 번들과 지정 방식(#38), 앱 배경 교체 UI(#29).

배경은 **장면별 값이 아니라 프로젝트 단위 값으로 정해졌다.** `project.json`의 `background`
섹션(`kind` / `value`)이 그것이고, `scenes.json`에는 배경 필드가 없다 — 장면 템플릿(#12)이
채울 것도 없다. 장면마다 다른 배경이 필요해지면 프리셋 이름을 정하는 #38이 함께 정한다.

**프리셋은 #38에서 확정됐다** — `deep_navy`(단색) / `purple_gradient` / `deep_teal_gradient`
(수직 2스톱). 값은 `assets/backgrounds/presets.json`에 있고 D1 확정 스펙 6.2가 근거다.
`render.background` 기본값이 `deep_navy`이며, 이름 → 정의값 조회는 `shorts_maker.assets`
하나다. 이미지·영상 배경은 프리셋과 다른 층이다 — `kind`가 `image`/`video`일 때 `value`가
사용자 파일 경로이고, 라이선스는 사용자가 확인하며 저장소에 들어오지 않는다.

#### 언어 타깃: 한국어 1차, `language` 필드로 확장 여지 유지

한국어를 1차 타깃으로 한다. 다국어 UI와 다국어 프롬프트는 MVP 범위가 아니다. 다만
`quiz.json` / `project.json`의 `language` 필드는 유지해 이후 확장 여지를 남긴다.

근거 — 프롬프트, TTS 음성, 폰트, 자막 줄바꿈 규칙이 모두 언어마다 다르다. 한 언어로 품질을
확정한 뒤 확장하는 편이 재작업이 적다. 스키마 필드만 미리 두면 확장 시 마이그레이션이 없다.

영향 — TTS provider 후보 범위(#2, 한국어 음성 품질이 선정 기준), 스키마 `language` 필드(#7).

#### LLM provider: 로컬 `claude` CLI 헤드리스 호출, 기본 모델 `claude-opus-5`

MVP는 로컬에 설치된 `claude` CLI를 헤드리스(`-p`)로 호출한다. 기본 생성 모델은
`claude-opus-5`(별칭 `opus`)로 한다. API 키 발급·보관이 MVP 범위에서 빠진다.

근거 — `opus` / `sonnet` / `haiku` 세 후보에 동일 프롬프트로 상식 퀴즈 4문제 생성을 3회씩,
블라인드 검증을 문제당 2회씩 총 33회 호출해 실측했다. 구조화 출력 실패율(전원 0%)과 정답
정확도는 후보를 변별하지 못했고, 실제로 갈린 것은 문제의 다양성과 난이도 보정이었다.
`opus`가 여기서 앞섰고, 문제당 지연은 `haiku`와 사실상 동일(26.9초 대 27.0초)했으며 비용
차이는 영상 1편당 $0.09 대 $0.05로 의사결정을 좌우하지 않는다. `sonnet`은 동일 프롬프트
3회 실행에서 같은 문제를 3회 전부 반복 출제해 탈락시켰다.

**이 결정은 오프라인 동작을 제공하지 않는다.** "로컬 claude"는 로컬에서 도는 LLM이 아니라
로컬 CLI를 통한 원격 API 호출이다. 오프라인이 요구사항으로 승격되면 재검토한다. 후보 3개가
모두 Anthropic 모델이므로 vendor 선택에 대한 답도 아니다 — provider 인터페이스를 vendor
중립으로 유지한다.

**호출 시 프로젝트 컨텍스트를 반드시 격리한다.** 격리 없이 호출하면 `CLAUDE.md`·스킬 목록·
툴 정의가 프롬프트에 실려 사소한 호출 하나가 $0.071까지 뛴다(격리 시 $0.004). 상세 플래그는
스파이크 문서 2.1에 있다. 격리는 adapter 내부에 고정하며 호출자가 끌 수 없다(#48).

**재시도는 결과가 달라질 수 있는 실패에만 적용한다.** `llm.max_retries`는 모델이 스키마를
맞추지 못했거나 응답 형태가 깨진 경우에만 쓰인다. 타임아웃과 바이너리 부재는 같은 조건에서
같은 결과가 나오므로 재시도하지 않는다 — 재시도하면 사용자 대기 시간만 `max_retries + 1`배가
된다. TTS provider(#14)도 같은 구분을 따른다.

영향 — config `llm.generator` / `llm.verifier` 키(#6), provider 레이어 구현(#48),
호출 지점(#9, #10, #13), 10장 기술 스택. 상세 실측치와 provider 인터페이스 스케치는
`docs/spikes/1-llm-provider.md`.

#### 타이밍 기준: 스펙의 초 단위 값은 목표치, 확정값은 실측 오디오 길이

낭독이 있는 장면의 `duration`은 합성된 오디오를 실측한 길이 + 앞뒤 패딩으로 확정한다.
스펙과 장면 템플릿의 초 단위 값(퀴즈 스펙 2장의 "질문 3초 / 정답 3초" 등)은 목표치이며
검증용 경고 기준으로만 쓴다. 낭독이 없는 장면(`countdown`, 현 스펙의 `hook`·`cta`)만
고정 길이를 쓴다. 기준값과 config 키는 7.5.1에 있다.

근거 — TTS 낭독 길이는 문장마다 다르다. 고정값을 쓰면 자막 타임코드, 카운트다운 오버레이,
정답 강조 애니메이션, 효과음 트리거가 모두 음성과 어긋나고, 어긋난 정도가 문장마다 달라서
후처리로 보정할 수도 없다.

**낭독 길이만으로는 부족한 경우가 하나 있다.** 해설처럼 낭독이 없고 자막으로만 전달되는
텍스트는 낭독 길이와 무관하게 읽을 시간이 필요하다. 그래서 확정 공식에 세 번째 항으로
자막 읽기 하한을 넣었다 (7.5.1). 분기 조건은 `role`이 아니라 `caption` 필드의 존재다.

영향 — 스키마의 duration·오프셋 필드(#7), 세그먼트 배치(#15), duration 보정 구현(#16),
자막 타임코드(#17), 렌더 타이밍(#19~#23).

#### 오디오 산출물: 장면별 세그먼트 + 타임라인 합성 트랙

`voice.mp3` 단일 파일이 아니라, 낭독 장면별 세그먼트(`audio/seg-{index:03d}.mp3`)와
이를 타임라인에 배치한 합성 트랙(`voice.mp3`)을 함께 남긴다. 파일 규격은 7.5.2에 있다.

근거 — 퀴즈는 카운트다운 구간에 낭독이 없어 연속된 단일 음성이 존재하지 않는다. 또한 편집
앱에서 한 문제의 정답 문구만 고쳤을 때 전체를 재합성하지 않으려면 세그먼트가 남아 있어야 한다.
세그먼트 파일명을 장면 인덱스로 매기는 것은 7.4.1의 타입 경계를 지키기 위한 것이다.

영향 — PRD 6.2 출력 목록, 스키마(#7), TTS 인터페이스(#14), 세그먼트 배치(#15), 앱 재렌더(#30).

#### 산출물 생성 조건: 타입·입력 경로에 따라 다르다

6.2의 출력 목록은 전부 항상 생성되는 목록이 아니다. `script.txt`는 내레이션 대본을 쓰는
타입만, `summary.json`은 원문 요약을 거칠 때만, `source.json`은 `--url`/`--text-file`
입력일 때만 생성한다. 세 파일 모두 퀴즈 타입 + `--topic` 경로에서는 생성되지 않으며, 없는
것이 실패가 아니다. 부류 구분은 6.2 표에 있다.

근거 — 없는 파일을 실패로 판정하거나 후속 단계가 존재를 전제하면, 퀴즈 타입 파이프라인이
정상 동작에서 오류를 내거나 빈 파일을 만들게 된다.

영향 — CLI 산출물 검증(#5), 스키마 검증기(#7), 타입 플러그인 인터페이스(#8), E2E 스모크(#24).

#### 기본 TTS provider: Edge TTS, 기본 음성 `ko-KR-SunHiNeural`

MVP는 `edge-tts`로 합성한다. 기본 음성은 `ko-KR-SunHiNeural`이며 config에서 교체한다.
호출 시 `boundary="WordBoundary"`를 명시한다 — 기본값은 `SentenceBoundary`이고 문장 단위
합성에서는 쓸모가 없다.

근거 — PRD 10장 후보 4개 중 실질 선택지가 하나였다. **Kokoro는 공식 `VOICES.md`에 한국어
섹션이 없어 탈락**했고(2차 자료 다수가 지원한다고 적지만 근거가 없다), OpenAI TTS와
ElevenLabs는 API 키가 필요해 7.5의 "무료 또는 로컬 실행이 쉬운" 기본값 조건에서 벗어난다.
Edge TTS는 세 가지를 실측으로 만족했다. 길이 측정이 두 방법에서 0.008초 안에 일치하고
(7.5.1의 전제), 같은 문장 3회 합성 길이가 완전히 동일하며(재실행 캐시의 전제), 숫자·단위·
기호 토큰 21개가 모두 한국어로 펼쳐 읽혔다. `ko-KR-InJoonNeural`은 모든 문장에서 8~18%
길어 60초 예산에서 불리하다.

**이 결정은 개인 로컬 사용을 전제한다.** `edge-tts`는 Microsoft Edge의 문서화되지 않은
엔드포인트를 호출하는 비공식 클라이언트다. 상류 저장소가 미션 크리티컬 용도를 권하지 않으며,
Microsoft가 이미 anti-abuse 토큰을 요구하도록 변경한 전례가 있어 예고 없이 깨질 수 있다.
상업적 사용·배포로 범위가 넓어지거나 엔드포인트가 막히면 **Azure AI Speech로 승격**한다 —
같은 Azure Neural 음성이라 `ko-KR-SunHiNeural`이라는 음성 이름이 그대로 유지되고 목소리가
바뀌지 않는다. 오프라인이 요구사항이 되면 MeloTTS-Korean(MIT)으로 간다.

**음질은 아직 판정하지 않았다.** 청취가 필요하고 스파이크는 청취하지 않았다. 샘플 39개와
청취 체크리스트가 스파이크 문서 7장에 있다. 음질이 기각되면 provider를 다시 열어야 한다.

부수 소득 — Edge TTS가 **단어별 오프셋과 지속시간**을 함께 주므로, 7.6의 word-level
timestamp 개선에 Whisper 전사가 필요하지 않을 수 있다. 전사는 추정이고 이 값은 합성 엔진의
실제 타이밍이다. 단 provider마다 제공 여부가 다르므로 인터페이스에서는 선택 기능으로 둔다.

영향 — config `tts.provider` / `tts.voice` 키(#6), TTS 인터페이스(#14), 세그먼트 배치(#15),
duration 보정(#16), 자막 타임코드(#17), 10장 기술 스택. 상세 실측치와 provider 인터페이스
요구사항은 `docs/spikes/2-tts-provider.md`.

#### 산출물 스키마: 코드가 단일 진실 공급원, `scenes.json`은 단일 스키마 + 확정 검증

`quiz.json` / `scenes.json` / `project.json`의 필드명과 열거값은 `src/shorts_maker/schemas/`가
확정한다. 문서(7.5.2, 7.10, 퀴즈 스펙 3장)는 그 이름을 설명하는 쪽이다. 세 파일 모두
`schema_version`을 가지며 모르는 버전은 오류다. `scenes.json`은 **스키마 하나에 오디오 필드를
optional로 두고**, TTS 이후 상태를 요구하는 확정 검증(`validate_scenes_final`)을 별도 함수로
분리한다. 확정 검증은 `narrate: true` 장면에만 오디오 필드를 요구한다.

근거 — 장면 템플릿이 만드는 것은 초안이고 오디오 필드는 TTS가 채운다(7.5.1, 7.5.2). 초안을
"필수 필드 누락"으로 떨어뜨리면 장면 템플릿이 자기 산출물을 검증할 수 없고, 반대로 초안용과
확정용 스키마를 따로 두면 공통 필드가 두 곳에서 갈라진다. 요구가 갈리는 축은 파일이 아니라
`narrate` 플래그이므로, 스키마는 하나로 두고 검증 함수를 나누는 것이 실제 구조와 맞는다.

`jsonschema`를 쓰지 않는다 — 이 계약의 핵심 규칙(`narrate` 조건부 필수, 세그먼트 파일명
인덱스와 장면 배열 위치의 일치)이 JSON Schema로 표현되지 않아 어차피 코드로 써야 하고,
조건부 규칙을 `allOf`/`if`로 우회하면 오류 경로가 `allOf[1].then.required`처럼 나와
"어느 필드가 틀렸는지"를 잃는다.

영향 — 산출물 검증(#8, #24), `quiz.json` 생성(#9)과 `verify` 필드(#10, #11), `scenes.json`
초안(#12), 오디오 필드 확정(#15, #16), 자막 오프셋 소비(#17), `project.json` 편집 상태 확장(#26).

#### 타입 플러그인: 선언은 타입 패키지가 소유하고 레지스트리는 이름만 안다

`src/shorts_maker/shorts_types.py`는 **타입 이름 → 선언 모듈 경로**만 가진다. 콘텐츠 생성기,
장면 템플릿, 산출물 선언은 그 타입의 패키지가 `SHORTS_TYPE: ShortsType`으로 소유하고
(`src/shorts_maker/types/quiz/__init__.py`), 레지스트리는 조회 시점에 import한다. 여기서
따라오는 것 셋:

- `--type`의 선택지와 `--help` 출력이 레지스트리에서 나온다. 미등록 타입은 CLI를 거치지 않는
  호출 경로에서도 `UnknownShortsTypeError`로 막힌다.
- `scenes.json` / `project.json`의 `type` 후보는 **검증 시점에** 레지스트리를 조회한다.
- 6.2 표의 `script.txt` / `summary.json` 생성 여부는 `ShortsType.produces_script` /
  `produces_summary`가 선언하고, 후속 단계는 파일 부재를 판정하기 전에 이 값을 본다.

근거 — 레지스트리에 타입 어휘(`quiz.json`, 생성기 구현)가 올라오면 두 번째 타입 추가가 그
파일부터 시작되고 7.4.1 경계에 구멍이 난다. `type` 후보를 import 시점에 상수로 고정하면
나중에 등록된 타입이 만든 산출물을 스키마가 반려한다. 산출물 조건이 호출부마다 다시 쓰이면
퀴즈 타입의 정상 동작이 "파일 없음" 오류가 된다(위 "산출물 생성 조건" 결정).

7.4.1의 경계는 문서가 아니라 테스트가 강제한다 — `src/shorts_maker/types/` 밖의 모듈이 타입
패키지를 import하거나 타입 전용 산출물을 직접 열면 `tests/test_type_boundary.py`가 깨진다.

영향 — CLI `--type`(#5), 스키마의 `type` 필드(#7), 퀴즈 생성기·장면 템플릿 등록(#9, #12),
산출물 검증(#24), 두 번째 타입 추가.

#### D1 영상 디자인: 수령 완료, 확정 스펙은 별도 문서

영상 안 화면 디자인(D1)을 외부에서 수령했고 이 저장소의 확정값과 대조해 정리했다.
좌표·크기·색·타이밍 전체는 [`docs/design/d1-video-design-spec.md`](design/d1-video-design-spec.md)에
있고, **원본 시안과 그 문서가 다르면 그 문서가 이긴다.** 여기서는 다른 장에 영향을 주는
것만 적는다.

- **고정 길이 장면 세 개가 짧아졌다** — `hook` 3.0→2.5초, `cta` 4.0→3.0초,
  `quiz.countdown_sec` 4→3. 시안이 그 길이로 프레임 레이아웃을 검증했고, 4문제 예산이
  52.2초에서 46.7초로 줄어 해설이 긴 문제의 읽기 하한에 쓸 여유가 생긴다 (7.5.1).
- **`scenes.json`에 통과 필드 두 개가 는다** — `heading`(블록 내내 상단에 유지되는 문구,
  퀴즈에서는 질문)과 `kicker`(본문 위 작은 라벨). 시안이 countdown·answer 장면에도 질문을
  띄우고 hook에 카테고리 라벨을 넣기 때문이다. 통과 필드는 `caption`과 같은 이유로
  타입 중립 이름을 쓴다 (퀴즈 스펙 1.1).
- **CTA의 고정 문구는 config에 둔다** — `render.cta_punch` / `render.cta_tail`. 채널
  브랜딩이라 LLM이 매번 새로 지을 값이 아니고, 타입 전용 정보도 아니다.
- **텍스트 길이 상한이 생성 단계로 올라간다** — `quiz.hook_max_len` 36 /
  `quiz.question_max_len` 45 / `quiz.cta_max_len` 24. 상한을 넘으면 레이아웃이 안전 영역을
  벗어나는데, 렌더 단계에서 잘라내면 사람이 검수할 원문이 사라진다.

근거 — 시안은 CSS로 그려졌고 렌더는 FFmpeg `drawtext`라서 같은 숫자가 같은 그림을 만들지
않는 지점이 셋 있다(외곽선 두께, 확대 중 중앙 정렬, 줄 간격). 그 셋은 실측 전까지 확정이
아니며 각각 #20·#22·#20의 첫 검증 항목으로 남겼다 — **셋 다 실측으로 닫혔다**
(확정 스펙 2장). 외곽선은 환산표의 절반값이 맞았고(정답 T1만 예외), 줄 간격은 줄마다
인스턴스를 나눠 역산이 사라졌고, 확대 중 중앙 정렬은 `text_w`·`text_h`가 매 프레임 갱신되어
표현식 하나로 성립한다.

영향 — 장면 길이 상수와 통과 필드(#12 후속), 생성 단계 길이 상한(#9 후속), 번인(#20),
카운트다운(#21), 정답 강조(#22), 효과음 트리거 시각(#23), 앱의 프리셋 선택(#29),
에셋 번들(#38).

#### TTS 길이 확정과 세그먼트 캐시: 계약에 길이가 없고, 캐시는 run 디렉터리 밖이다

`TTSProvider` 계약은 텍스트 하나를 오디오 파일 하나로 바꾸는 것까지만 하고 **길이를 돌려주지
않는다.** 실측은 공통 코드가 `ffprobe format=duration`으로 하고(`tts/speech.py`), 그 결과와
단어 타이밍을 묶은 값이 7.5.1의 입력이 된다. 캐시는 `(provider, voice, 원문 텍스트)` 해시를
키로 `tts.cache_dir`(기본 `.cache/tts`)에 오디오와 사이드카 JSON을 남긴다.

근거 — provider마다 길이 보고 정확도가 다르므로 계약에 길이 칸을 열면 adapter가 거짓말할
자리가 생기고, `duration`은 자막·오버레이·효과음이 전부 매달리는 값이라 측정 방법이 한
군데여야 한다. 캐시가 run 디렉터리 밖인 것은 run마다 새 디렉터리를 만들기 때문이다(13장) —
안에 두면 "같은 입력으로 반복 실행"이 매번 전부 재합성한다. 사이드카에 길이를 함께 두는 것은
적중할 때마다 `ffprobe`를 다시 부르면 캐시가 합성만 건너뛰는 데서 멈추기 때문이고, 같은
문장 3회 합성 길이가 완전히 동일했으므로(스파이크 #2 4.2) 적중과 미적중이 다른 값을 내지
않는다. 캐시 손상과 쓰기 실패는 실행을 멈추지 않는다 — 캐시는 속도를 위한 것이고, 디렉터리에
쓸 수 없다고 이미 만들어진 오디오를 버릴 이유가 없다.

**단어 타이밍의 `None`과 빈 목록은 다르다.** `None`은 provider가 주지 않는다는 뜻이고
(`supports_word_timings`가 false), 빈 목록은 주는데 이번 문장에서 하나도 오지 않았다는
뜻이다. 캐시 왕복에서 이 둘이 뭉개지면 #17이 "타이밍이 없다"와 "타이밍 기능이 없다"에 같은
대응을 하게 된다.

영향 — config `tts.timeout_sec` / `tts.max_retries` / `tts.cache_dir` 키(#6 후속), 7.5·7.5.2,
세그먼트 배치(#15), duration 보정(#16), 자막 타임코드(#17).

#### 효과음 레벨: 기본 게인은 감쇠 없이 1.0이고, 클리핑은 리미터가 막는다

효과음은 `audio.sfx_volume`(선형, 기본 `1.0`)으로 조정하고 `0`이면 효과음 없이 렌더한다.
믹스 끝의 리미터가 최종 오디오를 **-1 dBFS**에서 잡는다.

근거 — 실측에서 낭독(edge_tts `ko-KR-SunHiNeural`)은 peak -4.81 dBFS / RMS -18.06 dB이고
번들 효과음은 peak -14.3 dBFS / RMS -27~-28.5 dB였다. 대사 우선 믹스의 통상 범위(8~12dB)에
이미 들어 있으므로 기본 게인에 감쇠를 넣으면 근거 없는 상수가 하나 늘어난다. 동시 피크의
최악값도 -2.3 dBFS라 기본 설정에서는 리미터가 걸리지 않는다 — 리미터는 사람이 게인을 올린
경우와 낭독 레벨이 다른 provider를 위한 안전망이다. 상한을 설정 키에 두지 않는 이유가
그것이고, 음수만 거부한다.

**효과음이 낭독과 실제로 겹치는 곳은 정답 장면 하나다.** 정답 효과음은 장면 시작 +0.15초에
울리고 낭독은 +0.30초(`timing.lead_in_sec`)에 시작하므로 앞머리 약 0.5초가 겹친다.
카운트다운은 낭독이 없는 장면이라 겹치지 않는다.

영향 — config `audio.sfx_volume` 키(#6 후속), 7.7·7.10, `project.json`의 `audio` 섹션(#19 후속),
앱의 트랙 볼륨 편집(#29), 배경음악 ducking(#35)이 같은 리미터 뒤에 붙는다.

#### 앱 프레임워크와 백엔드 연결: Electron + React, 자식 프로세스 stdio (JSON Lines)

앱은 **Electron + React**로 만들고, Python 백엔드는 **앱이 자식 프로세스로 띄워 stdin/stdout
JSON Lines로 말한다.** 로컬 HTTP 서버를 열지 않는다 — 11장의 `api.py`는 HTTP 서버가 아니라
JSON Lines 디스패처다. Python 런타임은 **PyInstaller onedir로 동봉**하고 `assets/`를 실행 파일
옆에 둔다. **FFmpeg는 동봉하지 않고** CLI와 같이 PATH에서 찾는다.

근거 — 스파이크 #25(`docs/spikes/25-app-framework.md`)의 실측이다. Tauri v2는 Windows에서
MSVC Build Tools와 Rust 툴체인을 요구하는데 개발 환경에 셋 다 없어 빌드 자체가 되지 않았고,
Tauri의 크기 우위(Electron 런타임 348MB 대 수 MB)는 어느 쪽을 골라도 함께 지고 가는 Python
백엔드(26.9MB)와 FFmpeg(전체 빌드 462MB) 앞에서 희석된다. 전송은 stdio가 왕복 지연
0.033ms(HTTP 0.172ms / 파일 26.6ms)와 콜드 스타트 182ms(HTTP 673ms)로 앞서고, **부모를 강제
종료했을 때 HTTP·파일 백엔드는 살아남은 반면 stdio 백엔드만 함께 죽었다** — 앱이 크래시하면
렌더 중인 FFmpeg를 안은 백엔드가 남는다는 뜻이라 수명 관리 코드를 앱에 붙이지 않으려면 stdio다.
전 경로(React → main → Python → 화면)는 프로토타입에서 왕복 100회 중앙값 0.2ms로 동작한다.

**프레임 하나를 그릴 때마다 FFmpeg를 새로 띄우는 프리뷰는 성립하지 않는다.** 프리뷰 1프레임이
0.8~2.4초인데 그 바닥이 프로세스 기동이라(아무 일도 하지 않는 `ffmpeg -version`이 1.1초),
해상도를 1/4로 줄여도 빨라지지 않는다. #27이 장면 대표 프레임 배치 캐시를 골랐다 (아래 절).

**되돌리는 비용이 작다는 것이 이 결정의 안전장치다.** 백엔드는 프레임워크를 모르는 stdio
프로세스이므로, 설치 크기가 제품 요구가 되면 프론트 셸만 Tauri로 갈아 끼운다 — Tauri의
사이드카도 stdout/stdin으로 말한다.

영향 — 10장(기술 스택), 11장의 `api.py` 성격, 7.9의 프리뷰 구현 방식, 앱 이슈 #26~#30,
7.10이 "앱 프레임워크가 정해진 뒤"로 미뤄 둔 `project.json`의 편집 상태 필드(#29).

#### D2 앱 UI 디자인: 1차 배치 수령, 확정 스펙은 별도 문서

편집 앱 UI(D2)의 1차 배치를 외부에서 수령했다. 발주 내용은
[`docs/design/d2-app-design-brief.md`](design/d2-app-design-brief.md), 토큰·레이아웃·상태
표기 전체는 [`docs/design/d2-app-design-spec.md`](design/d2-app-design-spec.md)에 있고,
**원본 시안과 그 문서가 다르면 그 문서가 이긴다.** 여기서는 다른 장에 영향을 주는 것만 적는다.

- **S2는 목록 296 / 프리뷰 / 속성 340의 3분할이다.** 프리뷰가 재생되지 않는 정지 프레임이라
  화면 중앙을 크게 차지할 값이 없고, 우측 속성 패널이 #28·#29의 편집 폼이 얹힐 자리가 된다.
  2분할이면 편집을 모달로 띄워야 해서 고치면서 프리뷰를 볼 수 없다 (7.9).
- **`project.json`에 편집 상태 필드 두 개가 필요해졌다** — 낭독 트랙 볼륨과 사람 확인 기록.
  7.10이 "앱 프레임워크가 정해진 뒤"로 미뤄 둔 자리이고 프레임워크는 위에서 정해졌다.
  볼륨은 `audio` 섹션의 선형 게인이라 `audio.sfx_volume`과 같은 성격이다.
- **사람의 `flagged` 확인은 `quiz.json`의 `verify`를 건드리지 않는다.** 시안은 확인 버튼이
  `status`를 `verified`로, `confidence`를 `1`로 바꾸도록 그려져 있었으나, 그 두 값은
  `quiz_verifier`(#10)와 `quiz_review.py`(#11)가 소유한다. 사람 판단이 같은 칸을 쓰면
  다음 실행의 임계값 판정이 조용히 통과한다 — `verify.status`는 "정답이 맞다"가 아니라
  "검증 단계가 결함을 찾지 못했다"는 뜻이기 때문이다 (퀴즈 스펙 5.2). **기록 위치는 아래에서
  확정됐다.**
- **총 길이의 목표 범위 이탈은 경고가 아니라 정보다.** 3문제 구성은 정상 산출인데도 총
  길이가 38초대라 목표(45~60초) 아래로 내려간다. 경고 색으로 띄우는 것은 60초 초과뿐이다.

#### 사람의 검수 기록: `project.json`의 `review` 섹션

**사람이 `flagged`를 확인한 기록과 낭독 문구가 낡은 항목은 `project.json`의 `review`에
남긴다** — `acknowledged`와 `stale`, 둘 다 항목 번호 목록이고 스키마는
`schemas/project.py`에 있다 (7.10의 표).

근거는 소유권이다. `quiz.json`의 `verify.status`·`confidence`는 `quiz_verifier`(#10)와
`quiz_review.py`(#11)가 소유하는 판정 입력이고, 사람 판단이 그 칸을 덮으면 다음 실행의
임계값 판정이 조용히 통과한다. 확인은 **판정이 아니라 편집 상태**이므로 앱이 소유하는 파일에
있어야 하고, 그러면 `--fail-on-flagged`를 쓰는 자동화 경로는 사람 확인을 신뢰하지 않고
콘텐츠 산출물만 보면 된다 — 사람이 보는 화면과 게이트가 서로를 오염시키지 않는다.

번호가 타입 어휘가 아닌 이유는 `scenes.json`의 `question_id`가 **이미 공통 스키마의
필드**이기 때문이다 (7.4.1). 공통 계층은 그 번호가 무엇의 번호인지 모른 채 같은 값을 참조한다.

- **장면 순서·개수가 낡았는지는 적지 않는다.** 콘텐츠의 번호 나열과 `scenes.json`의
  `question_id` 나열을 비교하면 나오는 값이라, 기록하면 두 곳이 다른 말을 할 수 있다.
- **`stale`은 되돌려도 떨어지지 않는다.** `scenes.json`이 어느 문구에서 만들어졌는지 기록해
  두는 곳이 없어 비교 기준이 "직전 값"뿐이다. 낡지 않은 것을 낡았다고 말하는 쪽이 반대보다
  안전하고, 표시를 지우는 것은 재생성(#77)이다.
- **앱 백엔드는 콘텐츠 산출물의 이름을 모른다.** `api.py`는 `types/` 밖이라 `load_quiz`도
  `"quiz.json"`도 쓸 수 없으므로(퀴즈 스펙 1.1), 파일명과 검증을 `ShortsType.content_schema`
  에서 받는다. `config_check`·`content_review`와 같은 성격의 선언이고 **교체 가능한 축은
  여전히 생성기·장면 템플릿 둘뿐이다.**

영향 — 7.10의 `project.json` 스키마, 11장의 `api.py` 메서드 목록(`content` / `save_content`),
퀴즈 스펙 8장의 앱 편집 항목, #30의 렌더 전 경고가 읽는 확인 상태.
- **총 길이의 목표 범위 이탈은 경고가 아니라 정보다.** 3문제 구성은 정상 산출인데도 총
  길이가 38초대라 목표(45~60초) 아래로 내려간다. 경고 색으로 띄우는 것은 60초 초과뿐이다.

근거 — 시안이 저장소의 확정값을 세 군데 잘못 알고 있었고 전부 실측으로 닫혔다(확정 스펙
1장). 자막 스타일과 배경의 권장 짝 두 개가 서로 바뀌어 있었고(`neon_mint`↔`orange_card`,
`assets/caption-styles/presets.json`이 확정값), 고정 장면 길이가 D1 이전 값이었고,
`text/3` 토큰이 11px 문구에서 4.08:1로 소형 텍스트 AA에 미달했다. D1과 달리 CSS→렌더 번역
단계가 없어(Electron + React) 나머지 수치는 시안 값이 그대로 구현값이다.

영향 — 앱 이슈 #26~#30, 7.10의 `project.json` 편집 상태 필드, 8장의 검수 게이트가 앱에서
완성되는 지점(#30). S1(프로젝트 열기)과 S4(텍스트 오버레이·자막 텍스트 편집)는 #27 머지 후
2차 배치로 받는다.

#### 프리뷰 프레임: 요청이 하나든 전부든 FFmpeg 프로세스는 하나다

프리뷰는 **장면 대표 프레임(장면 한가운데)을 프로세스 하나로 전부 만들어 캐시에 넣는다.**
캐시 키는 `project.json` + `scenes.json`의 지문이고, 지문이 바뀌면 통째로 버리고 다시 만든다.
프레임은 run 디렉터리 밖(백엔드 프로세스 수명의 임시 디렉터리)에 둔다. 스파이크 #25 6장이
남긴 세 길 중 첫 번째(장면 대표 프레임 캐시)이며, 그 문서가 전제하지 않은 조건 하나가 붙었다 —
**다시 만들 장면을 골라 봐야 아끼는 것이 거의 없다.**

근거 — [`docs/spikes/27-preview-frames.md`](spikes/27-preview-frames.md)의 실측이다(11장면 /
27.9초 / 837프레임, 3회 중앙값). 장면마다 프로세스를 띄우면 합계 19,131ms인데 한 프로세스로
전부 만들면 2,247ms다(8.5배). 필터는 마지막 요청 프레임까지 어차피 돌므로 **뒤쪽 장면 하나만
만드는 데 2,049ms, 전부 만드는 데 2,247ms** — 재생성 범위를 좁히는 코드는 198ms를 위해
복잡도를 진다. 절대값은 프로세스 기동이 바닥이라 실행마다 ±20% 흔들리고, 결론이 걸려 있는
것은 비율이다. 두 방식이 낸 PNG는 파일 크기까지 같았고, 같은 이유로 프리뷰와 최종 렌더도
갈릴 수 없다(둘 다 `video_renderer._video_stage` 하나를 지난다).

화면에서는 **장면 이동이 3~5ms(캐시 적중), 값 변경이 2초대**가 된다. 7.9의 대기 표현이 두
가지인 이유가 여기서 나온다 — 장면 이동은 즉시라 이전 프레임을 지워도 빈 화면이 보이지 않고,
값 변경은 기다리므로 지우면 비교할 대상이 사라진다.

**오래 걸리는 백엔드 메서드는 스레드로 나간다** (`api.BACKGROUND_METHODS`). 2~3초 동안
디스패치 루프를 잡고 있으면 앱은 저장도 다른 요청도 하지 못한다. 응답은 `id`로 짝을 찾으므로
순서가 뒤바뀌어도 앱이 헷갈리지 않는다. #30의 렌더가 같은 자리를 쓴다.

재검토 조건 — 장면이 30개를 넘거나 총 길이가 2~3분대가 되면 배치 한 번이 6초를 넘길 수 있다.
그때 상주 프레임 서버(스파이크 #25 6장의 2번)를 다시 잰다.

영향 — 7.9(프리뷰 구현), 11장의 `api.py` 메서드 목록, #30(렌더 진행률이 같은 스레드 경로를
쓴다), #36(프리뷰 실패는 `code: "render"`로 온다).

#### 사람이 얹은 장면 편집: `project.json`의 `render.scene_overrides`

**사람이 조정한 장면 길이·자막 문구·텍스트 오버레이는 `project.json`의 `render` 섹션에 얹고,
`scenes.json`은 건드리지 않는다.** 세 편집이 항목 하나(`role` + `question_id`)에 `duration` /
`text` / `overlays`로 함께 붙는다 — 저장 위치를 나누면 같은 장면을 가리키는 키가 세 벌 생긴다.
길이는 #82, 문구와 오버레이는 #83이 채운다.

**선택지가 하나뿐이다.** `validate_scenes_final`이 `duration`이 `audio_duration`보다 짧은
장면을 거부하므로(`schemas/scenes.py`, 7.5.1), 낭독보다 짧은 값을 `scenes.json`에 쓰면 앱의
저장이 실패하고 그 run 디렉터리는 다시 열리지도 않는다. #29의 완료 조건은 **경고하되 값은
받는** 쪽이므로(D2 확정 스펙 5장) 그 값이 살 수 있는 자리는 `project.json`뿐이다. "재실행이
실측으로 되돌린다"는 우려는 성립하지 않는다 — CLI는 매번 새 run 디렉터리를 만들므로 되돌릴
원본이 없고, 같은 디렉터리를 고쳐 쓰는 것은 앱과 재생성(#77)뿐이다.

- **키는 장면 인덱스가 아니라 `role` + `question_id`다.** 인덱스는 문제를 추가·삭제하면
  밀리고, 그러면 조정한 길이가 다른 장면에 붙는다 — #28이 새 문제 번호에서 같은 종류의 함정을
  밟았다. 두 값은 이미 `scenes.json`의 공통 어휘이므로 타입 경계를 넘지 않는다 (7.4.1).
- **`countdown`은 이 경로에 들어오지 않는다.** `duration`이 `seconds`와 같아야 하고
  (`schemas/scenes.py`) 그 값은 콘텐츠 필드라 #28의 문제 편집에 이미 있다.
- **적용 지점은 `align()` 앞이다.** 프레임 정렬을 소유하는 함수는 그대로 하나여야 한다
  (7.7). `render` 섹션이므로 프리뷰 지문에 들어가고(`APP_STATE_SECTIONS`가 아니다) 값을
  고치면 프레임이 다시 만들어진다.
- **길이를 고치면 `captions.srt`와 `voice.mp3`가 어긋난다.** 이후 장면의 시작 시각이 전부
  밀리기 때문에, 낡는 대상이 특정 항목이 아니라 타임라인 전체다. `review`의 어느 칸으로
  표시할지는 하위 이슈가 #77과 함께 정한다 — 항목 번호 목록인 `stale`로는 표현되지 않는다.
- **오버레이와 자막 문구를 `scenes.json`에 두면 재생성이 지운다.** 그 파일은 파이프라인이
  소유하는 확정 산출물이므로 #77이 장면을 다시 만들 때 사람이 넣은 값이 사라진다. D2 2차
  시안이 제안한 `scene.overlays`를 그대로 옮기면 그 경로에 들어간다 (D2 확정 스펙 7.1).

영향 — 7.10의 `project.json` 스키마, 7.7(프레임 정렬), #82(길이), #83(문구·오버레이), #77.

#### 낡음은 두 종류다: 자막만 / 음성까지

**"오디오·자막이 낡았다"를 한 상태로 두지 않는다.** 사람이 자막 문구만 고친 경우와 낭독되는
문장을 고친 경우는 다시 만들어야 하는 산출물이 다르고, 앱은 그 둘을 아이콘 모양과 문구로
구분해 보여준다 (D2 확정 스펙 7.3 — 색은 둘 다 `accent`다).

- **해설은 낭독되지 않으므로 자막만 낡게 한다.** `scene_template`이 해설을 `caption`으로만
  담고 TTS는 `narrate: true` 장면의 `text`만 읽는다 (7.5.2, `narration.py`). 해설을 고쳤을 때
  음성을 다시 만들면 같은 오디오를 다시 합성하는 비용만 든다.
- 낡음이 한 종류였을 때는 해설을 낭독 문구에 함께 넣는 것이 맞았다 — 자막이 낡는 것은
  사실이기 때문이다. 두 종류로 갈린 뒤에는 그 분류가 과잉이 된다 (#28의 `narration()`).
- 두 상태가 함께 걸릴 수 있고, 음성 재생성이 자막 재생성을 포함한다.

영향 — 7.10의 `review` 섹션(목록이 갈린다), #28의 낭독 문구 판정, #83, #77.

#### 배경 사용자 파일의 지원 형식: PNG · JPG · MP4(H.264)만 받는다

**앱이 배경으로 받는 사용자 파일은 `.png` / `.jpg` / `.jpeg` / `.mp4`뿐이고, 나머지는 이유를
표시하며 거부한다** (webm 포함). `background.kind`는 확장자가 정한다 — 앞의 셋이 `image`,
`mp4`가 `video`다.

좁게 시작하는 이유는 **실패 시점**이다. FFmpeg는 동봉하지 않고 PATH에서 찾으므로(10장) 앱은
사용자 환경의 빌드가 무엇을 디코드하는지 알 수 없다. 넓게 열면 파일을 고르는 순간이 아니라
수십 초 걸리는 렌더 도중에 실패한다. 목록은 필요할 때 넓히는 쪽이 안전하다.

- **목록은 렌더러가 소유하고 앱은 조회한다.** 자막 스타일 이름을 `assets/`가 소유하는 것과
  같은 이유다 — 앱과 CLI가 각자 목록을 들면 앱이 받은 파일을 렌더가 거부할 수 있다.
- 거부는 D2 확정 스펙 4장의 **`danger`(거부)** 이고, 낭독보다 짧은 길이는 **`warn`(경고,
  값은 적용된다)** 이다. 두 색이 뜻이 다르므로 같은 표시를 쓰지 않는다.
- 파일은 run 디렉터리로 복사하지 않는다. 경로 값은 상대 경로가 기본이지만 절대 경로도
  받으므로(7.10, `video_renderer._source_file`) 사용자 파일은 있는 자리를 가리킨다.

영향 — 7.10의 `background` 필드, #29의 배경 교체 하위 이슈, D2 확정 스펙 6장.
